# Transport выполняет команды, facts меняются по ОС

Выполнить команду на машине - обязанность transport. Transport это соединение и операции через него: прочитать файл, выполнить команду, сходить по сети. Facts-модуль собирает данные только через transport, и его внутренняя изменчивость идет по операционной системе, а не по способу доступа: хост читается ровно тем же кодом, что guest, потому что хост - это локальный transport, реализованный системными вызовами.

## Considered Options

Альтернатива - facts backend на каждый transport: плагин SSH регистрирует свой сбор фактов и держит внутри собственное соединение. Отклонена, потому что тогда доступ к машине существует в двух местах одновременно - как порт transport и приватно внутри каждого бэкенда, - а знание «`python3 --version` значит вот такой факт» дублируется в каждом бэкенде. Плагин про SSH становится плагином про SSH и про факты, то есть отвечает за две вещи.

## Consequences

`output` и окружение процесса openstrap (`stateHome`, `PATH` процесса) в порт transport не входят: печати прогресса внутри VM не существует. Порт не отдает производных данных - определение ОС в transport не живет, иначе знание про ОС уезжает в адаптер и facts-модуль перестает собирать.

`FactsBackend.capabilities.transports` теряет смысл, а сам порт facts backend остается оправданным только для принципиально другого механизма сбора - например osquery одним запросом вместо десяти команд.

> Пересмотрено в ADR 0007. Порт `FactsBackend` удален: пока CLI выбирает бэкенд, входов в модуль фактов два, а требование - один. Утверждение «хост читается ровно тем же кодом, что guest» осталось, но исполняется иначе - код доставляется на машину, а не разбирает ее вывод через transport.

Сбор фактов должен уметь ждать сеть, поэтому он не выполняется в конструкторе: модуль facts создает инстанс и предоставляет API.
