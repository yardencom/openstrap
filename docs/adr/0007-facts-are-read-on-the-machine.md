# Факты собираются на самой машине, а не о ней

Факты читаются через API машины и на самой машине. Способ сбора один, и он не знает, где запущен: `new Facts().collect(order)` читает машину, на которой идёт этот процесс. Машины, до которой openstrap дотягивается только через transport, для модуля фактов не существует.

Дотягивается openstrap тем, что доставляет туда **сам себя**: `RemoteOpenStrap` кладёт на цель сборку openstrap для её платформы и запускает `openstrap facts collect --json --order <base64>`. Отдельной программы-агента нет. Она была - и дублировала команду, которая у openstrap уже есть; openstrap по ADR 0001 всё равно обязан поставляться одним самодостаточным файлом, то есть он и есть то, что нужно положить на машину.

Заказ (`FactOrder`) несёт три вещи, которых машина о себе знать не может: как её называет вызывающий, какие секции объявлены, и через какой канал до неё дошли. Канал даёт тот, кто его открыл, - `authMethods` сообщает соединение, а не блюпринт. Ничего не открывали - секции `transports` в снимке нет: openstrap, читающий машину, на которой он запущен, канала не открывал, и `local` в этом месте был выдумкой, против которой проходило требование.

Модуль фактов не импортирует ни transport, ни что-либо ещё за своими границами - это проверяется тестом. Доставка живёт в `src/RemoteOpenStrap` и не собирает фактов - тоже проверяется тестом. Как только одно возьмёт на себя работу другого, реализаций снова станет две.

## Considered Options

**Разбирать вывод программ через transport.** Отклонено: это вторая реализация того же самого. Хост читался бы через `node:os`, гость - через `ps`/`systemctl`/`df`, и две реализации расходятся. Это уже было сделано и уже сломалось: снимок гостя оказался несравним со снимком хоста, а `ps -axo comm` на BSD обрезал имя процесса до 16 символов, из-за чего 678 из 680 процессов назывались `/System/Library/`. Плюс `wmic` - удалённая программа в Windows 11, то есть путь без будущего.

**Читать `/proc` и `/sys` гостя через `FileSystemAPI`.** Отклонено: чисто по API и без доставки чего-либо, но на macOS нет `/proc`, а без него список процессов не получить никак. Модуль перестал бы работать одинаково для хост/гость - ровно то ограничение, которое требовалось убрать.

**osquery как facts backend плагина.** Отклонено как основной механизм: требует установки на цель. Чтение машины не должно её менять.

## Consequences

`FactsBackend` как порт плагина удалён вместе с реестром, `--facts-backend`, `openstrap.config.mjs → facts.backend` и плагином `openstrap:core`. Оговорка ADR 0002 - «порт остаётся оправданным для принципиально другого механизма сбора» - не выдержала требования единственного входа: пока CLI выбирает бэкенд, входов два. Второй реализации не существует, а порт под гипотетическую реализацию - это порт, который никто не проверяет.

openstrap собирается для целевых платформ `esbuild` + `@yao-pkg/pkg` (ADR 0001) в `dist/remote/openstrap-<os>-<arch>`, `npm run remote:build`, из той же точки входа `src/CLI/index.ts`, которую запускает человек. Поэтому в `index.ts` нет top-level await, а `import.meta.url` в бандле объявлен отсутствующим: где лежат свои файлы, openstrap отвечает из исполняемого файла, которым его запустили. Кросс-сборка идёт с `--no-bytecode`: кэш байткода V8 валиден только для того V8, который его создал, и цель отвергает его при старте.

Цена - 63 МБ на архитектуру. Файл называется по sha256 своего содержимого, поэтому неизменённая сборка не отправляется дважды, а изменённую нельзя спутать со старой; дайджест пишется при сборке, а не считается при каждом чтении. Предыдущая сборка удаляется, когда приходит новая, и какая это была - записано на цели: цель хранит тот openstrap, которым её читают, а не все, что ей когда-либо присылали.

`openstrap facts collect` не пишет ничего никуда. Снимки прогона хранит state store; вторая копия в `.openstrap/runs/facts/<id>/result.json` была вторым хранилищем того же самого, и записывать что-либо нельзя на машине, которую попросили только прочитать.

Какая машина на другом конце, определяется чтением заголовка `/bin/sh`: ELF против Mach-O даёт ОС, `e_machine`/`cputype` - архитектуру. Это не факт и в снимок не попадает - это выбор сборки. Читается файл, а не запускается `uname`, потому что до доставки openstrap запускать на цели нечего.

Два исключения из «только API» названы в коде там, где сделаны. Пароль для `sudo`: ни один API не отвечает, работает ли `sudo` без пароля, потому что единственное доказательство - что он сработал. И программы, которые объявил сам вызывающий: openstrap не решает запустить программу, он запускает ровно объявленное.

Служба считается present, когда она запущена. Установленная, но остановленная служба читается как absent - это самое сильное утверждение, верное на всех платформах: launchd не даёт спросить о существовании label, не спрашивая о загруженности. Поле `running` несёт тот же ответ явно, поэтому требование можно написать в любую сторону.

Юзеры и группы читаются одним кодом на всех ОС - из `/etc/passwd` и `/etc/group`, потому что эти файлы и есть интерфейс: формат, в котором каждая POSIX-система объявляет свои локальные аккаунты. Отличается не чтение, а полнота файла на конкретной платформе, и это отличие сообщается, а не заглаживается. На Linux файл и есть локальная база аккаунтов, поэтому отсутствующее в нём имя - `absent`. На macOS локальные аккаунты живут в directory service, которого файл не покрывает: `/etc/passwd` содержит только системные записи, а `/var/db/dslocal` без root не читается - поэтому отсутствующее имя `unknown`, а не `absent`. Сказать `absent` было бы неверным фактом, что хуже неполного.

Аккаунт, от которого идёт чтение, всегда отвечен полностью на любой ОС - `node:os` сообщает о нём напрямую, - и всегда присутствует в секции `users` под своим именем: снимок, который не говорит, кем он снят, нельзя сравнить со следующим. Его группы берутся из `process.getgroups()`, то есть из того, что реально выдало ядро: членство, выданное directory service, есть там и нет ни в одном файле. Для группы, найденной на платформе с неполным файлом, ставится `reason: members_may_be_incomplete` - группа есть, а кто ещё в ней, этот файл решить не может.

`users` и `groups` - карты по имени, как `processes` и `services`, потому что вопрос ставится так же: «есть ли юзер `openstrap`». Секция `sessions` facts definition объявить позволяет, а чтение не отвечает: она перечислена в `DeclaredFacts.unread` и печатается как «Declared but not read», потому что определение, которое молча собирает девять секций из десяти, хуже определения, которое собирает девять и говорит об этом.

Вход в модуль - `new Facts(...)`, и метод у инстанса один: `collect(order)`. Раньше дверей было две - `openstrap facts collect` входил через `collectFromDefinition`, а `run` и `create` через `collect`.

Самостоятельного файла фактов не существует. Формат facts definition удалён целиком: `Facts/Definition/`, его JSON-схема, `schemas/facts-definition.schema.json` и примеры в `examples/facts/`. Что читать, говорит вызывающий, и единственный конфиг, который это говорит, - блuprint; его читает модуль `Blueprint`, а `RequiredFacts` выводит из требований объявление. Побочный итог: модуль `Facts` больше не зависит от `ConfigCore` и не содержит ни одного формата файла - оговорка теста независимости про `Definition/` исчезла вместе с папкой.

`openstrap facts collect host` остался и ничего не объявляет: он читает машину как она есть, без требований и прочих намерений блuprint. Сравнивает - `openstrap run`, эта команда только смотрит. Ордер, не назвавший ничего, законен: секции, отвечающие без имён, отвечают, а те, что держат названные вещи, остаются пустыми - придумывать в них записи значило бы придумывать факты.

Секция `transports` есть в снимке только тогда, когда канал действительно открывали. При чтении в своём процессе канала нет - `никакой LocalTransport не нужен`, - поэтому секция пуста. Раньше туда безусловно писалось `local: { status: present, ready: true }`, и требование `local-transport` в примере проходило против этой выдумки; требование убрано. Для реального канала `present` и `ready` - не утверждение, а свидетельство: код доходит до этой точки только после того, как чтение вернулось через этот канал.

Как канал аутентифицировался, сообщает `TransportConnection.authMethods` - то есть тот, кто аутентифицировался. Раньше фасад писал `authMethods: ["publickey"]`, если transport назывался `ssh`, то есть выводил факт из текста блuprint: требование `key-only-login` проверяло значение, которое openstrap сам же и записал, и прошло бы на соединении по паролю. Теперь фасад записывает только то, что ему сообщили, и ничего - если не сообщили.

`contains` в требованиях был объявлен в схеме и не реализован в вычислителе: список сравнивался на равенство целиком. Реализован - требование «аккаунт входит в `sudo`» спрашивает о членстве, а не о полном совпадении набора групп.
