# Вход: для человека и для автоматизации

Задача, над которой идёт работа. Два разных входа, потому что у них разные условия: у человека
есть браузер и учётная запись, у агента нет ни того, ни другого.

## Человек

`openstrap login` — device authorization grant. Команда показывает короткий код и адрес, человек
вводит код там, где уже вошёл, команда дожидается подтверждения.

```
$ openstrap login
Open https://provider.example/device and enter WDJB-MJHT. Waiting.
```

Полученное сразу меняется на машинный токен и не сохраняется: то, чем человек входит, принадлежит
ему и его провайдеру, а на машине остаётся пропуск, который сервер может отозвать отдельно.

**Сделано**

- `GET /v1/auth` — сервер сам говорит, кто у него провайдер входа. Клиент этим не настраивается.
- `DeviceLogin` — запрос кода, показ, опрос в назначенном темпе (`authorization_pending`, `slow_down`).
- `POST /v1/tokens` — сервер выпускает машинный токен и показывает его один раз, хранит только хеш.
- `openstrap login` — проводит всё это и кладёт токен в хранилище секретов плагина.
- `openstrap login --forget` — убирает токен, машина возвращается к работе в одиночку.

**Не проверено**

Целиком не запускалось ни разу: сервер не поднят, провайдер входа в его конфигурации не задан.
Проверено только то, что проверяется без них — команда сообщает о недоступном сервере и не делает
вид, что вошла.

**Осталось**

- Поднять сервер и настроить провайдера, пройти вход живьём.
- Первый вход, когда провайдера нет вовсе: предъявлять серверу нечего, и первый пропуск приходится
  создавать на нём напрямую. Сейчас выхода из этого нет.

## Автоматизация

Агент, CI, что угодно без браузера. Device flow там бессмыслен — некому вводить код.

Путь — машинный токен: он выпускается на сервере (`POST /v1/tokens`, `ost_…`) и кладётся в
окружение агента. Проверка такого токена на сервере уже есть — сверка хеша в `api_token`,
с учётом срока и отзыва.

**Сделано**

- `openstrap tokens issue <name>` — человек, который уже вошёл, выпускает пропуск для агента и
  кладёт его туда, где агент будет искать. Показывается один раз: сервер хранит только хеш.
- `openstrap tokens` — что вообще выпущено, без самих пропусков.
- `openstrap tokens revoke <id>` — забрать обратно. Помечается, а не удаляется: строка, которой
  нет, не может ответить, когда и почему пропуск перестал работать.
- На сервере: `GET /v1/tokens`, `POST /v1/tokens/:id/revoke`.

**Осталось**

- Агент сам себя не заводит и не должен: пропуск ему выпускает человек. Но как этот пропуск
  попадает в агента — не решено. Переменные окружения запрещены, файл с секретом тоже.
- Срок: `expires_at` сервер принимает и проверяет, но `openstrap tokens issue` его не задаёт.
- `openstrap login` для агента по-прежнему бесполезен — всегда идёт в device flow.

## Где лежит

| Что | Где |
|---|---|
| Клиент: обмен и хранение | `src/CLI/application/LoginCommand.ts` |
| Клиент: device flow | `src/Api/DeviceLogin.ts` |
| Клиент: адрес сервера и обмен на токен | `src/Api/OpenStrapServer.ts` |
| Сервер: кто подписывает вход | `openstrap-server/src/http/HttpApi.ts` — `GET /v1/auth` |
| Сервер: выпуск токена | `openstrap-server/src/application/Tokens.ts` |
| Сервер: проверка токена | `openstrap-server/src/auth/Authentication.ts` |
